## (d) Decisions

1. **Planner settings skew local plans toward seq scans** (prod vs local): `random_page_cost` 1.1 vs 4, `effective_cache_size` 3GB vs 128MB, `work_mem` 7MB vs 4MB, `jit` off vs on, `effective_io_concurrency` 200 vs 1, `max_parallel_workers_per_gather` 1 vs 2. Not applied (would shift perf baselines). To match:
   ```sql
   ALTER DATABASE postgres SET random_page_cost = 1.1;
   ALTER DATABASE postgres SET effective_cache_size = '3GB';
   ALTER DATABASE postgres SET work_mem = '7MB';
   ALTER DATABASE postgres SET jit = off;
   ALTER DATABASE postgres SET effective_io_concurrency = 200;
   ALTER DATABASE postgres SET max_parallel_workers_per_gather = 1;
   ```
2. **`publication_pages.leaflet_src`, `metadata`, `published_metadata`**: migration `20260609000001` says they "go away" but never drops them; committed types had them hand-removed. Regenerated types include them. Write a drop migration (destructive on prod) or accept them.
3. **`documents_indexed_at_idx`** has 0 prod scans on a 2.1 GB table: pure write cost. In the catch-up only for parity; could be dropped in prod.
4. **`leaflet_page_result`** is dead: keep, or drop in prod and from the catch-up.
5. **`publication_email_posts.leaflet` one-to-one**: committed types hand-set `isOneToOne: true`; the DB has a unique index, not a constraint, so the generator says `false` (tsc passes either way). For one-to-one embeds: `ADD CONSTRAINT ... UNIQUE USING INDEX publication_email_posts_leaflet_key`.
6. **Hand-written drizzle `check()` entries and `unique("publication_membership_tiers_id_publication_key")`** on `publication_membership_tiers` are gone: drizzle-kit 0.21 can't introspect CHECK constraints; they only matter for drizzle-kit push/generate, which the repo doesn't use.
7. **`database.types.ts` is public-schema only** now; the `graphql_public` and `storage` blocks are dropped (nothing imports them).
8. **CI connection string**: the `prod-schema-drift` job builds the session-pooler URL from the existing `SUPABASE_DB_PASSWORD` secret and the project ref (the direct `db.<ref>` host is IPv6-only). That's the read-write postgres role `deploy-supabase` already uses; a read-only login role would be tighter.
9. **Prod max rows**: confirm in the dashboard. If 100k, set `max_rows = 100000` in `config.toml` and the harness role setting becomes unnecessary.
10. **Local column order on `publication_pages`**: only `supabase db reset` fixes it (wipes local data). Optional.

## Type generation

`scripts/generate-db-types.mjs` (local by default, `--prod` for production, `--check` to diff against the committed files):

- uses the pinned supabase 1.187.3 and drizzle-kit 0.21.4 from node_modules;
- always passes `--db-url`; sets `DB_URL` only for the drizzle child process; hides the connection string in error output;
- deterministic output: `--schema public` only; strips extension-owned functions (pg_trgm lives in `public`); strips non-public enums; sorts drizzle imports, tables, columns, indexes and relations by name.

- two catalog-driven corrections the pinned CLI gets wrong: GENERATED ALWAYS columns (`documents.identity_did`) are `?: never` on Insert/Update, and `RETURNS TABLE` columns listed in `NULLABLE_RETURNS` (`get_facts_*.author_did`) stay `| null`, since Postgres records no nullability for function output.

prod, fresh and local produce byte-identical files, and `npx tsc` passes with them (after adding `identity_did` to the object literal in `PublishedPostsLists.tsx`).

Differences from the previously committed (hand-maintained) files: objects never typed (`document_feed_publication`, `documents.identity_did`, and in drizzle `comment_tombstones`, `document_tags`, `email_render_images`, `publication_email_posts`, `publication_scheduled_posts`, `reply_drafts`, `stripe_*`, `tag_counts`, ~20 relations blocks); hand edits undone (d2, d5, d6); noise removed; a one-time reshuffle from sorting.

## CI

1. **PR check** (`test-integration.yml`): path filter also covers `supabase/database.types.ts`, `drizzle/**` and the wrapper; after `./.github/actions/run-tests` (which runs `supabase start` on a fresh migrate) it runs `node scripts/generate-db-types.mjs --check`. Untested risk: `supabase/setup-cli@v1` installs the latest CLI, which may boot a newer Postgres image that renders expressions differently; if so, pin `version: 1.187.3`.
2. **Prod check** (`main.yml`): job `prod-schema-drift`, `needs: deploy-supabase`, builds `PROD_DB_URL` from `SUPABASE_DB_PASSWORD` (masked in logs) and runs `node scripts/generate-db-types.mjs --prod --check`; never commits.

Fails on: a migration merged without regenerated types, hand edits to generated files, dashboard/hand DDL in prod, bumping supabase or drizzle-kit, or a migration that behaves differently on prod than on a fresh DB.
